Client settings on every engine provider (#149). Elasticsearch and OpenSearch get `RequestTimeout` and `MaxRetries`, and Meilisearch gets `RequestTimeout`, in `SharedIndexSettings` or an `Indexes` entry; an entry that leaves one out takes the shared value, and unset keeps the client's default. The options validators check them at startup, naming the setting: `RequestTimeout` must be greater than 0 and `MaxRetries` must not be negative. Typesense's existing `RequestTimeout` is now validated too: it must not be negative, and `00:00:00` still means no timeout. Behavior change: a negative Typesense `RequestTimeout`, which used to mean no timeout, now fails startup validation. `AddElasticSearch`, `AddOpenSearch`, `AddMeilisearch` and `AddTypesense` take a new optional `configureClient` parameter (`Action<ElasticsearchClientSettings>`, `Action<ConnectionSettings>` and `Action<HttpClient>`), run on each client after the options are applied, once per cached client. The timeout and retry count are part of the client cache key, so indexes with different values get different clients. Adding the parameter changes the signature of those four public methods, so code compiled against an earlier beta must be recompiled.
