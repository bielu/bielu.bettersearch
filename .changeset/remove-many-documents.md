Add `RemoveDocumentsAsync(index, ids)` to `IIndexingServiceAsync` and `IIndexingProviderAsync`, removing many documents in one call (#19). It returns how many documents were removed: an id that is not in the index is not counted and is not an error, a repeated id is removed once, and an empty list succeeds with 0 without calling the engine. A `null` list, or a `null` or empty id, is a failed `Result` and removes nothing. Elasticsearch and OpenSearch send one bulk request; when some items fail, the `Result` fails with a message naming up to 20 failing ids, the error's `ids` metadata holding all of them, and the other documents are already removed. A request cancelled through the `CancellationToken` throws `OperationCanceledException` on Elasticsearch and OpenSearch, and a request rejected as a whole fails with a short message naming the HTTP status and the server's error. Meilisearch sends one deletion task, which succeeds or fails as a whole, and keeps Meilisearch's error code in the `code` metadata; when the wait for the task times out (`TaskTimeout`), the `Result` fails saying the task may still remove any or all of the ids, with its uid in the `taskUid` metadata. Every Meilisearch write that times out now carries that `taskUid` metadata. Lifti removes the ids one by one, from the index its client factory returns, under the same per-index lock as `RemoveDocumentAsync`, and a cancelled token throws `OperationCanceledException`. A missing index is a failed `Result` on Elasticsearch, OpenSearch and Meilisearch, and success with 0 on Lifti, as with `RemoveDocumentAsync`. On success, the service sends one `DeleteDocumentRequest` to its observers for each distinct id; a failed `Result` sends nothing. Breaking: a custom `IIndexingServiceAsync` or `IIndexingProviderAsync` must implement the new method.
