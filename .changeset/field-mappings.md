Add field mappings to the Elasticsearch and OpenSearch providers (#18). `SharedIndexSettings.Mappings` and each `Indexes` entry's `Mappings` list fields with a `Type` (`Text`, `Keyword`, `Date`, `Long`, `Integer`, `Short`, `Byte`, `Double`, `Float`, `Boolean` or `GeoPoint`) and an optional `Analyzer` (text) or `Format` (date); an index's mappings add to the shared ones and replace a shared mapping of the same field. `CreateIndexAsync` creates the index with them, and `EnsureIndexExistsAsync` also adds them to an existing index, returning a failed `Result` naming the field when one conflicts with the field's current mapping, and a failed `Result` saying the mappings may still apply when the cluster does not acknowledge them in time. A `Text` field gets a `keyword` sub-field (`ignore_above` 256), and sorting on it uses that sub-field under the plain field name; `TermQuery` and `TermsQuery` on it match one token of its analyzer, which with the default analyzer is one word. A `Keyword` field matches and sorts on its whole value under its plain name, and a `GeoPoint` field makes `SpatialSearchQuery` work. Fields not listed keep dynamic mapping. The options are validated at startup with `ValidateOnStart`, and an invalid mapping throws `OptionsValidationException` naming the setting.

Behavior change: Elasticsearch `CreateIndexAsync` used to report any rejection, such as a 401, as success with `false`; it now returns `false` only when the index already exists and a failed `Result` otherwise, as OpenSearch does. OpenSearch's create failure message is now the short HTTP status and server error rather than the full debug information.

Breaking: the public `ElasticSearchIndexingProviderAsync` and `ElasticSearchSearchProviderAsync` constructors take an `IElasticSearchClientSettingsManager`. Code that resolves them through DI is unaffected.
