# BetterSearch Provider Feature Matrix

What each provider really does today. This is a beta: see [roadmap](../../ROADMAP.md) for the plan.

✅ works · ⚠️ works with the caveat noted · ❌ not available

Elasticsearch and OpenSearch documents are stored with their values under `fields`, so a query on `Name` searches `fields.Name`. Metadata fields such as `_id` and `_score` pass through unchanged; any other name, including one starting with `_` such as `_tags`, is a document field. A query missing a value it needs, such as `Field`, returns a failed `Result`.

Elasticsearch and OpenSearch create indexes with dynamic mapping, which makes a string a `text` field with a `keyword` sub-field, unless it looks like a date, which date detection maps as `date` with no sub-field. `SharedIndexSettings.Mappings` and each `Indexes` entry's `Mappings` map fields explicitly (`Text`, `Keyword`, `Date`, the numeric types, `Boolean` or `GeoPoint`, with an optional `Analyzer` or `Format`); fields not listed keep dynamic mapping, and invalid mappings fail at startup. A `Keyword` field matches and sorts on its whole value under its plain name. A `Text` field matches one token of its analyzer in `TermQuery` and `TermsQuery`, which with the default analyzer is one word, as on every provider, and sorts on its `keyword` sub-field automatically. See [the Elasticsearch page](providers/elasticsearch.md#field-mappings).

Query values that are not strings are turned into text the same way on every machine: booleans in lower case (`true`), numbers with the invariant culture, so a query sends `3.5`, not `3,5`, on a machine running under a culture such as `pl-PL`, and dates in ISO 8601 as UTC. A `DateTime` with `Kind.Local` and a `DateTimeOffset` are converted to UTC, a `DateTime` with `Kind.Unspecified` is taken as UTC, fractional seconds are written only when they are not zero (`2026-11-08T13:05:00Z`, `2026-11-08T13:05:00.123Z`), and a `DateOnly` is `2026-11-08`. Elasticsearch, OpenSearch and Meilisearch also store date field values as that text, so a date comes back from a search in UTC and a Term, Terms or Prefix query with a date value on a keyword field (`Born.keyword`) matches the stored date. A text field holds the date split into words by its analyzer, so query the keyword field for a whole date. On a field Elasticsearch or OpenSearch mapped as a date, which dynamic mapping does for these strings, they reject a Prefix or PrefixPhrase query. Documents indexed before this version keep the text the client wrote then (no `Z` for an unspecified date, the offset for a local one), so re-index them. Lifti also indexes field values that way and splits text into words at punctuation and spaces, so a decimal such as `3.5` is indexed as the words `3` and `5`, and a date as its parts (`2026`, `11`, `08T13`, `05` and `00Z`). It splits a Term, Terms, Fuzzy, Prefix or PrefixPhrase value with the same tokenizer and matches the words next to each other, in order, so a whole decimal, date or exponent (`1E-07`) matches the value it was indexed from, a Fuzzy `3.5` does not match `35`, and a single part of a date (`2026`) still matches too. A Prefix value ending with punctuation or a space (`3.`) matches its last word whole, followed by any word, so `3.` matches `3.5` but not `35` or `3`; that following word can be the next value of a multi-valued field. Words from different values of a multi-valued field are never next to each other, so `3.5` does not match `["3", "5"]`. A value with no words, such as `null`, `""` or `-`, returns a failed `Result`, and so does a Terms query with such a value in its list; a Terms query whose list is `null` or empty succeeds with no hits.

Meilisearch queries run as filters, which compare whole values, so the provider also stores each text field's words lower-cased (`tokens`), the word runs a phrase prefix can start at (`phrases`, up to 16 words, for every field or only those in `MeilisearchOptions.PhraseFields`) and each date as Unix milliseconds (`dates`). A query on `Name` filters those copies; a query on `fields.Name` compares the value as given, as `Name.keyword` does on Elasticsearch. Words split on anything that is not a letter or digit. A field name can only contain letters, digits, `_`, `-` and `.`; any other returns a failed `Result`. When `MeilisearchOptions.GeoField` is set, the provider also copies that field's point to `_geo`, and indexing a document whose point is not valid returns a failed `Result`. Documents indexed before this version have no copies, so re-index them.

| **LuceneQuery** (raw Lucene syntax) | ⚠️ field names need the `fields.` prefix | ⚠️ field names need the `fields.` prefix | ⚠️ parsed with Lucene.NET's `QueryParser` and translated into one filter. Field names work with or without the `fields.` prefix, and either way a term matches as TermQuery does on the field's words, never as the whole value. Terms, a trailing `*` prefix, ranges (bounds that read as numbers or ISO 8601 dates also compare numbers or dates; a date without a time rounds as on Elasticsearch: up to the end of the day for an included maximum or an excluded minimum), `_exists_:f`, `f:*`, `AND`, `OR`, `NOT`, `+` and `-` translate exactly. Two kinds translate only approximately, and the result carries a `TranslationWarning`: a fuzzy term (`jane~`) matches the exact word, and a quoted phrase of 2 to 16 words (`"jane doe"`, `"jane-doe"`) matches a run of words starting with it while the field also holds its last word anywhere, as Meilisearch trims the trailing space a filter would need to end the run there. A quoted single word (`"jane"`) is a term: exact, with no warning and no `PhraseFields` check. A term without a field, an unquoted term that splits into several words (`Name:foo-bar`; `Name:(jane doe)` is two terms joined with `OR`, and translates), an empty phrase (`""`), proximity (`"a b"~2`), boosts (`^2`), regular expressions, any other wildcard and parentheses nested more than 32 deep return a failed `Result`; so does a phrase of several words on a field outside `MeilisearchOptions.PhraseFields` | ❌ |
| **DateRangeQuery** | ✅ | ✅ | ✅ | ❌ |
| **NumericRange** | ✅ | ✅ | ✅ | ❌ |
| **LongRange** | ✅ | ✅ | ⚠️ Meilisearch compares numbers as doubles, so values past 2^53 lose precision | ❌ |
| **StringRange** | ⚠️ compares analyzed tokens to the bounds as given, so bounds are case-sensitive (`"A"`–`"Z"` misses the token `jane`); use `Field.keyword` for whole values | ⚠️ compares analyzed tokens to the bounds as given, so bounds are case-sensitive (`"A"`–`"Z"` misses the token `jane`); use `Field.keyword` for whole values | ⚠️ compares lower-cased words, and one word must lie inside the range, as on Elasticsearch; use `fields.Name` for whole values, which compare ignoring case | ❌ |
| **SpatialSearchQuery** | ⚠️ the field must be mapped as `GeoPoint` in `Mappings`; dynamic mapping doesn't create one | ⚠️ the field must be mapped as `GeoPoint` in `Mappings`; dynamic mapping doesn't create one | ⚠️ only on the field named by `MeilisearchOptions.GeoField`, as Meilisearch filters by distance on one `_geo` attribute; that field holds one point, a `"lat,lon"` string or a dictionary with `lat` and `lon`, and the provider copies it to `_geo`; unset, a failed `Result` | ❌ |

Every sub-query starts as `Occurance.MUST` with a `BoostValue` of 1, so one put in a bool's `NestedQueries` directly, or by a collection initializer, is a `MUST` clause; `Add` sets the occurrence it is given. Both edges of a range (`IncludeMinEdge`, `IncludeMaxEdge`) are inclusive by default, on the model and in the fluent API's `WithMinValue` and `WithMaxValue`, so a range from 25 to 30 matches 25 and 30; set an edge to `false` to exclude it. A `DateRangeQuery`, `NumericRange`, `LongRange` or `StringRange` with neither `MinValue` nor `MaxValue` returns a failed `Result` on every provider, Lifti included, with the same message (`NumericRange has neither MinValue nor MaxValue; set at least one bound.`), rather than matching every document that has the field. A Lucene range with no bounds (`Age:[* TO *]`) is not affected. `NumericRange` holds `double?` bounds, so a range can be fractional (9.99 to 49.5); a bound is not rounded, so at least 4.5 matches the whole number 5 and not 4, and a `NaN` or infinite bound returns a failed `Result` on every provider (`NumericRange has a bound that is not a finite number; use a finite MinValue and MaxValue.`). Use `LongRange` for whole numbers that need precision above 2^53. A `DateRangeQuery` bound is a `DateRangeValue`, which a `DateTime` or a `DateTimeOffset` converts to implicitly, and compares instants on every provider: a `DateTimeOffset` keeps its instant whatever its offset, a `DateTime` with `Kind.Local` is converted to UTC, and one with `Kind.Unspecified` is read as UTC, never as the machine's or the server's time zone. Shared tests check a fractional range with values just inside and just outside each bound, a fractional bound on whole numbers, and dates and bounds written with different offsets, on Elasticsearch, OpenSearch and Meilisearch, and that Lifti fails them.

The query model and fluent API can express sorting, facets, highlighting and post filters. Elasticsearch, OpenSearch and Meilisearch apply sorting and post filters, and Elasticsearch and OpenSearch highlight; Lifti applies none of them and fails a query that asks for highlighting.

`SortOrderField` is the `ISortOrderField` to put in `SortOrder`. Keys apply by `Order`, lowest first, and keys with the same `Order` keep their place in the list. Every provider, Lifti included, returns a failed `Result` for a `null` entry (`SortOrder holds a null entry.`) or an entry whose `FieldName` is `null`, empty or blank (`A SortOrder entry needs a FieldName.`), before it sends anything to the engine. The shared `SortingTestBase` checks both messages on every provider, and a two-key sort returning a fixed order on Elasticsearch, OpenSearch and Meilisearch; on Lifti it checks that the order is the one without `SortOrder`.

Setting `SearchDocument.Fields` to `null`, in code or by deserializing, gives an empty dictionary, so a document always has fields. `IIndexingServiceAsync.IndexDocumentAsync` returns a failed `Result` naming the fields whose value is `null` rather than a list, or naming the fields that hold a `null` value; use an empty list for a field with no values. `IndexMultipleDocumentsAsync` checks every document for `null` first, failing on a `null` entry too, and indexes none of them when one has a `null`. A document the validator rejects or the engine fails on also fails the batch, but the documents before it are already stored. A rejected `null` sends nothing to the indexing observers. `RemoveDocumentsAsync(index, ids)` returns how many documents it removed, counting a repeated id once and not counting an id that is not there; an empty list succeeds with 0 without calling the engine, and a `null` list or a `null` or empty id is a failed `Result` that removes nothing. A failure message names up to 20 ids, and the error's `ids` metadata holds all of them. On success the service sends one `DeleteDocumentRequest` per distinct id to its observers, and a failed `Result` sends nothing, even for documents already removed. The providers' own `IIndexingProviderAsync.IndexDocumentAsync` does not check this and stores the document. A document stored with `null` fields, a `null` field or a `null` value, through a provider or by another writer, is still searchable on every provider; Elasticsearch, OpenSearch and Meilisearch map hits through the same code, so they return `null` fields as no fields, a `null` field as an empty list, leave `null` values out of a list and return the same CLR types for the same stored value, and Lifti returns only ids.

On Elasticsearch and OpenSearch, `WriteVisibility` in `SharedIndexSettings` or an `Indexes` entry decides when a successful write returns. `Default` returns once the write is stored, and a search sees it after the next index refresh, about a second later; `WaitUntilSearchable` adds `refresh=wait_for` to index, delete and bulk requests and `refresh=true` to the delete by query of `RemoveAllDocumentsAsync`, so the write is searchable when the call returns. Whatever the setting, `RemoveAllDocumentsAsync` refreshes the index before its delete by query, which would otherwise skip writes not refreshed yet, and a failed refresh is a failed `Result` that removes nothing. An `Indexes` entry without it takes the shared value. Each call can then wait up to the refresh interval, and `IndexingServiceAsync.IndexMultipleDocumentsAsync` indexes one document at a time, so it waits once per document. Meilisearch and Lifti have no such setting, as their writes are already searchable on return.

Meilisearch applies writes as tasks; the provider waits for each one, so a successful `Result` means the write was applied and a failed task returns Meilisearch's error with its code in the error's `code` metadata. If the wait times out (`MeilisearchOptions.TaskTimeout`, 30 seconds by default) the `Result` fails but the task is not cancelled, so the write may still be applied later; the error's `taskUid` metadata holds the task's uid. Writes also check the index's settings and, when something is missing, add the attributes the provider filters and sorts on and raise `pagination.maxTotalHits` to `MaxTotalHits`. Attributes added by others and a higher `maxTotalHits` are kept. A check is trusted for `MeilisearchOptions.SettingsCheckInterval` (5 seconds by default), so an index deleted elsewhere is fixed by the first write after that, and a higher `MaxTotalHits` by the next write.

## Test coverage

Provider-agnostic bases live in `BaseTests`. Lifti runs all three (`SubQueryTranslationTestBase`, `IndexingTestBase`, `QueryResultBaseTests`), plus its own search tests running every supported query type, boolean combinations, paging, sorting, result mapping and error paths; the unsupported query types are checked to fail, and the known defects (ignored `Field`, ignored paging and sorting, id-only hits, `CreateIndexAsync` replacing an index, a search creating a missing index) are pinned as they behave today. Its culture tests index and query a decimal, a `DateTime`, a `DateTimeOffset`, a date prefix and exponents end to end, and check that a decimal matches neither `35` through a Fuzzy query nor its words held in separate values. Its indexing provider tests cover bulk indexing across indexes, remove-all, index deletion, every write that needs an index failing when none can be created, and removing one or many documents failing when the index lookup fails (removing never creates an index), throwing when cancelled, removing from the index the client factory returns, and not recreating an index deleted between the lookup and the remove; removing one document also keeps a thrown exception as the cause. The nested and top-level boolean semantics are shared tests there, so every provider must agree on them. Elasticsearch runs all three against a real server, plus its own search tests running every query type except `SpatialSearchQuery` against it, with boolean combinations, paging, sorting, result mapping and error paths. OpenSearch runs the same three bases and the same search tests against a real OpenSearch 3.3 server, plus provider tests for bulk indexing, remove-all and configuration. Both run the same mapping tests against their server: a `Keyword` field matched and sorted under its plain name, a `Text` field sorted on its `keyword` sub-field (case, multi-valued, `ignore_above` and a field named `fields`), a sort on `_score` kept on relevance when a `Text` field is named `_score`, an unmapped field kept dynamic, `SpatialSearchQuery` on a `GeoPoint` field, a `Date` field with the format `strict_date_optional_time||yyyy-MM-dd` accepting a `DateTime` and a `DateOnly` and finding each through `DateRangeQuery`, the mapping applied by `CreateIndexAsync` and added by `EnsureIndexExistsAsync`, a conflicting mapping and an unknown analyzer failing, and invalid options failing startup validation. Meilisearch runs all three against a real server too, plus its own search tests running every supported query type, `SpatialSearchQuery` included, boolean combinations, paging, sorting, result mapping and error paths; the unsupported query types are checked to fail. `SearchableWritesTestBase` runs on every provider, with Elasticsearch and OpenSearch set to `WaitUntilSearchable`: it indexes three documents one at a time, then two in a batch, removes one, then two, then all, and searches straight after each write, with no sleep and no manual refresh, for exactly the documents left. The `QueryResultBaseTests` cancel a search (also one whose query is invalid), check that searching a missing index returns a failed `Result` (skipped on Lifti, which creates the index), round-trip a mixed-case id, return a hit whose stored field is `null`, return a document whose `Fields` was set to `null` as one with no fields, and filter by culture through the fluent API on every provider; the culture test is skipped on Lifti, which ignores the field, and a Lifti test checks instead that the other cultures are left out and that the document holding the culture value in its title matches too. They also return stored strings, whole numbers, fractional and whole `double`s (`4.5` and `3.0`) and booleans as `string`, `long`, `double` and `bool` on Elasticsearch, OpenSearch and Meilisearch; on Lifti, which returns only ids, that test checks the hit's id alone. They also return stored dates (an unspecified `DateTime` with milliseconds, a UTC `DateTime`, a `DateTimeOffset` with an offset and a `DateOnly`) as ISO 8601 text in UTC on those three. Elasticsearch and OpenSearch also index dates into an index without date detection, check the text stored for each, and match a `DateTime` and a `DateTimeOffset` Prefix value on `Born.keyword`. Some base tests assert returned values, not only `IsSuccess`: the index tests check, each on an index of its own, that a created index exists, a deleted one does not and a missing one reads as `false`, that creating a new index, deleting an index and `EnsureIndexExistsAsync` on an existing or a missing index succeed with `true`, and that eight concurrent `EnsureIndexExistsAsync` calls on a missing index all succeed with `true`, and bulk indexing returns its count; the `RemoveDocumentsAsync` tests check the removed count, which documents are left, a repeated id, an empty list, `null` ids, a missing index and the observers; translation checks that a supported query yields a query and an unsupported one an error message. Others, such as indexing or deleting a single document, still assert only `IsSuccess`. `FluentApi` is tested through `FilterByCulture` on every provider, and its own test project, `Bielu.BetterSearch.FluentApi.Tests`, builds each range query (numeric, long, string and date) and checks both bounds and both edge flags, checks that a date bound given as a `DateTimeOffset` keeps its instant and that a `DateTime` of each kind becomes the instant in UTC, an unspecified one read as UTC, and checks the occurrence of the clause each query type builds, at the top level and in a bool: a sub-query's own `Must()`, `Should()`, `MustNot()` or `Filter()` wins, without one it takes its parent's, a bool is added under its parent's occurrence while `Should()` and the others on it set its clauses' default, and the clauses of a nested bool default to `MUST`. It also checks the `ISearchQuery` each other builder method gives: the spatial centre, the fuzzy options, raw Lucene, boost (a boost of 0 or less throws), sorting, returned properties, post filters, highlighting, and that `WithSearchQuery` keeps the query passed to the constructor. These tests check the query model the fluent API builds, not what an engine does with it.
