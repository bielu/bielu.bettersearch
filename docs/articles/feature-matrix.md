# BetterSearch Provider Feature Matrix

What each provider really does today. This is a beta: see [roadmap](../../ROADMAP.md) for the plan.

✅ works · ⚠️ works with the caveat noted · ❌ not available

Elasticsearch and OpenSearch documents are stored with their values under `fields`, so a query on `Name` searches `fields.Name`. Metadata fields such as `_id` and `_score` pass through unchanged; any other name, including one starting with `_` such as `_tags`, is a document field. A query missing a value it needs, such as `Field`, returns a failed `Result`.

Meilisearch queries run as filters, which compare whole values, so the provider also stores each text field's words lower-cased (`tokens`), the word runs a phrase prefix can start at (`phrases`, up to 16 words, for every field or only those in `MeilisearchOptions.PhraseFields`) and each date as Unix milliseconds (`dates`). A query on `Name` filters those copies; a query on `fields.Name` compares the value as given, as `Name.keyword` does on Elasticsearch. Words split on anything that is not a letter or digit. A field name can only contain letters, digits, `_`, `-` and `.`; any other returns a failed `Result`. When `MeilisearchOptions.GeoField` is set, the provider also copies that field's point to `_geo`, and indexing a document whose point is not valid returns a failed `Result`. Documents indexed before this version have no copies, so re-index them.

| **TermQuery** (exact term match) | ⚠️ matches one analyzed token, ignoring ASCII case only (`Żółw` does not match `żółw`); use `Field.keyword` for the whole value | ⚠️ matches one analyzed token, ignoring ASCII case only (`Żółw` does not match `żółw`); use `Field.keyword` for the whole value | ⚠️ a string matches one word, ignoring case (`Żółw` matches `żółw`); `fields.Name` matches the whole value, also ignoring case (`WARSAW` matches `Warsaw`), as Meilisearch compares every string that way, unlike `Name.keyword`; a string that reads as a number or boolean (`"30"`, `"true"`) also matches that value; numbers, booleans and dates match the value, on `fields.Name` too | ⚠️ field ignored; accented terms don't match |

The query model and fluent API can express sorting, facets, highlighting and post filters. Elasticsearch, OpenSearch and Meilisearch apply sorting and post filters; Lifti reads none of them.

| Persistence | ✅ | ✅ | ✅ | ❌ in memory only, lost on restart |

`IIndexingServiceAsync.IndexDocumentAsync` returns a failed `Result` when the document's `Fields` is `null`, naming the fields whose value is `null` rather than a list, or naming the fields that hold a `null` value; use an empty list for a field with no values. `IndexMultipleDocumentsAsync` checks every document for `null` first, failing on a `null` entry too, and indexes none of them when one has a `null`. A document the validator rejects or the engine fails on also fails the batch, but the documents before it are already stored. Either method calls `OnCompleted` on the indexing observers when it rejects a `null`. The providers' own `IIndexingProviderAsync.IndexDocumentAsync` does not check this and stores the document. A document stored with `null` fields, a `null` field or a `null` value, through a provider or by another writer, is still searchable on every provider; Elasticsearch, OpenSearch and Meilisearch return `null` fields as no fields, a `null` field as an empty list and leave `null` values out of a list, and Lifti returns only ids.

Meilisearch applies writes as tasks; the provider waits for each one, so a successful `Result` means the write was applied and a failed task returns Meilisearch's error with its code in the error's `code` metadata. If the wait times out (`MeilisearchOptions.TaskTimeout`, 30 seconds by default) the `Result` fails but the task is not cancelled, so the write may still be applied later. Writes also check the index's settings and, when something is missing, add the attributes the provider filters and sorts on and raise `pagination.maxTotalHits` to `MaxTotalHits`. Attributes added by others and a higher `maxTotalHits` are kept. A check is trusted for `MeilisearchOptions.SettingsCheckInterval` (5 seconds by default), so an index deleted elsewhere is fixed by the first write after that, and a higher `MaxTotalHits` by the next write.

## Test coverage

Provider-agnostic bases live in `BaseTests`. Lifti runs all three (`SubQueryTranslationTestBase`, `IndexingTestBase`, `QueryResultBaseTests`). The nested and top-level boolean semantics are shared tests there, so every provider must agree on them. Elasticsearch runs all three against a real server, plus its own search tests running every query type except `SpatialSearchQuery` against it, with boolean combinations, paging, sorting, result mapping and error paths. OpenSearch runs the same three bases and the same search tests against a real OpenSearch 3.3 server, plus provider tests for bulk indexing, remove-all and configuration. `SpatialSearchQuery` is only checked to translate, as it needs an explicit `geo_point` mapping. Meilisearch runs all three against a real server too, plus its own search tests running every supported query type, `SpatialSearchQuery` included, boolean combinations, paging, sorting, result mapping and error paths; the unsupported query types are checked to fail. The `QueryResultBaseTests` cancel a search (also one whose query is invalid), round-trip a mixed-case id, return a hit whose stored field, or whose whole `fields`, is `null` and filter by culture through the fluent API on every provider; the culture test is skipped on Lifti, which ignores the field. Most of these tests assert `IsSuccess` without checking the returned value, and `FluentApi` is only tested through `FilterByCulture`.
