# BetterSearch Provider Feature Matrix

What each provider really does today. This is a beta: see [roadmap](../../ROADMAP.md) for the plan.

✅ works · ⚠️ works with the caveat noted · ❌ not available

Elasticsearch and OpenSearch documents are stored with their values under `fields`, so a query on `Name` searches `fields.Name`. Metadata fields such as `_id` and `_score` pass through unchanged; any other name, including one starting with `_` such as `_tags`, is a document field. A query missing a value it needs, such as `Field`, returns a failed `Result`.

Elasticsearch and OpenSearch create indexes with dynamic mapping, which makes a string a `text` field with a `keyword` sub-field, unless it looks like a date, which date detection maps as `date` with no sub-field. `SharedIndexSettings.Mappings` and each `Indexes` entry's `Mappings` map fields explicitly (`Text`, `Keyword`, `Date`, the numeric types, `Boolean` or `GeoPoint`, with an optional `Analyzer` or `Format`); fields not listed keep dynamic mapping, and invalid mappings fail at startup. A `Keyword` field matches and sorts on its whole value under its plain name. A `Text` field matches one token of its analyzer in `TermQuery` and `TermsQuery`, which with the default analyzer is one word, as on every provider, and sorts on its `keyword` sub-field automatically. See [the Elasticsearch page](providers/elasticsearch.md#field-mappings).

Query values that are not strings are turned into text the same way on every machine: booleans in lower case (`true`), numbers with the invariant culture, so a query sends `3.5`, not `3,5`, on a machine running under a culture such as `pl-PL`, and dates in ISO 8601 as UTC. A `DateTime` with `Kind.Local` and a `DateTimeOffset` are converted to UTC, a `DateTime` with `Kind.Unspecified` is taken as UTC, fractional seconds are written only when they are not zero (`2026-11-08T13:05:00Z`, `2026-11-08T13:05:00.123Z`), and a `DateOnly` is `2026-11-08`. Elasticsearch, OpenSearch and Meilisearch also store date field values as that text, so a date comes back from a search in UTC and a Term, Terms or Prefix query with a date value on a keyword field (`Born.keyword`) matches the stored date. A text field holds the date split into words by its analyzer, so query the keyword field for a whole date. On a field Elasticsearch or OpenSearch mapped as a date, which dynamic mapping does for these strings, they reject a Prefix or PrefixPhrase query. Documents indexed before this version keep the text the client wrote then (no `Z` for an unspecified date, the offset for a local one), so re-index them. Lifti also indexes field values that way and splits text into words at punctuation and spaces, so a decimal such as `3.5` is indexed as the words `3` and `5`, and a date as its parts (`2026`, `11`, `08T13`, `05` and `00Z`). It splits a Term, Terms, Fuzzy, Prefix or PrefixPhrase value with the same tokenizer and matches the words next to each other, in order, so a whole decimal, date or exponent (`1E-07`) matches the value it was indexed from, a Fuzzy `3.5` does not match `35`, and a single part of a date (`2026`) still matches too. A Prefix value ending with punctuation or a space (`3.`) matches its last word whole, followed by any word, so `3.` matches `3.5` but not `35` or `3`; that following word can be the next value of a multi-valued field. Words from different values of a multi-valued field are never next to each other, so `3.5` does not match `["3", "5"]`. A value with no words, such as `null`, `""` or `-`, returns a failed `Result`, and so does a Terms query with such a value in its list; a Terms query whose list is `null` or empty succeeds with no hits.

Meilisearch queries run as filters, which compare whole values, so the provider also stores each text field's words lower-cased (`tokens`), the word runs a phrase prefix can start at (`phrases`, up to 16 words, for every field or only those in `MeilisearchOptions.PhraseFields`) and each date as Unix milliseconds (`dates`). A query on `Name` filters those copies; a query on `fields.Name` compares the value as given, as `Name.keyword` does on Elasticsearch. Words split on anything that is not a letter or digit. A field name can only contain letters, digits, `_`, `-` and `.`; any other returns a failed `Result`. When `MeilisearchOptions.GeoField` is set, the provider also copies that field's point to `_geo`, and indexing a document whose point is not valid returns a failed `Result`. Documents indexed before this version have no copies, so re-index them.

Typesense queries run as filters too, and a Typesense collection has a schema, so the provider creates each collection with one field pattern per kind of value and stores, for a field `Name`, a JSON copy of every field for results (`source`), the words lower-cased (`t_Name`), each string whole (`s_Name`), the word runs a phrase prefix can start at (`p_Name`), integers as `int64` (`i_Name`), other numbers as Typesense `float`s (`n_Name`), dates as Unix milliseconds (`d_Name`), booleans (`b_Name`), the point of `TypesenseOptions.GeoField` (`g_Name`) and, for a field holding one value, a sortable copy. Typesense fails a filter on a field no document has, so a search reads the collection's fields (trusted for `TypesenseOptions.SchemaCheckInterval`, and read again for a field not in the list once the list is a second old, or at once after a write through the provider) and treats such a comparison as matching nothing. A field name can only contain letters, digits and `_`. See [the Typesense page](providers/typesense.md).

Every sub-query starts as `Occurance.MUST` with a `BoostValue` of 1, so one put in a bool's `NestedQueries` directly, or by a collection initializer, is a `MUST` clause; `Add` sets the occurrence it is given. Both edges of a range (`IncludeMinEdge`, `IncludeMaxEdge`) are inclusive by default, on the model and in the fluent API's `WithMinValue` and `WithMaxValue`, so a range from 25 to 30 matches 25 and 30; set an edge to `false` to exclude it. A `DateRangeQuery`, `NumericRange`, `LongRange` or `StringRange` with neither `MinValue` nor `MaxValue` returns a failed `Result` on every provider, Lifti included, with the same message (`NumericRange has neither MinValue nor MaxValue; set at least one bound.`), rather than matching every document that has the field. A Lucene range with no bounds (`Age:[* TO *]`) is not affected. `NumericRange` holds `double?` bounds, so a range can be fractional (9.99 to 49.5); a bound is not rounded, so at least 4.5 matches the whole number 5 and not 4, and a `NaN` or infinite bound returns a failed `Result` on every provider (`NumericRange has a bound that is not a finite number; use a finite MinValue and MaxValue.`). Use `LongRange` for whole numbers that need precision above 2^53. A `DateRangeQuery` bound is a `DateRangeValue`, which a `DateTime` or a `DateTimeOffset` converts to implicitly, and compares instants on every provider: a `DateTimeOffset` keeps its instant whatever its offset, a `DateTime` with `Kind.Local` is converted to UTC, and one with `Kind.Unspecified` is read as UTC, never as the machine's or the server's time zone. Shared tests check a fractional range with values just inside and just outside each bound, a fractional bound on whole numbers, and dates and bounds written with different offsets, on Elasticsearch, OpenSearch and Meilisearch, and that Lifti fails them.

The query model and fluent API can express sorting, facets, highlighting and post filters. Elasticsearch, OpenSearch, Meilisearch, Typesense and PostgreSQL apply sorting and post filters, Elasticsearch, OpenSearch and Meilisearch apply facets (Meilisearch only top-level term facets), and Elasticsearch and OpenSearch highlight; Lifti applies none of them and fails a query that asks for facets or highlighting.

### Facets

Each entry in `FacetQueries` comes back in `ISearchResult.Aggregations`, in the same order, and `RetrieveBucketAggregation(name)` and `RetrieveSingleAggregation(name)` find one by its `AggregationName`, on the result or on a bucket's `Aggregations`. A `TermAggregation` or `MultiTermAggreation` gives a `BucketAggregation` with one `KeyBucket` per value or combination, the values with the most documents first; `Size` sets how many, 10 when it is 0 (`TermAggregation.DefaultSize`). A multi-term bucket has every field's value in `Keys`, `IsComplex` set, and the engine's joined key (`Red|acme`) in `Key`. A `FilterAggregationQuery` gives a `SingleAggregation` with one `SingleBucket` holding the number of documents its `Queries` match. Nested facets are counted per bucket, in the bucket's `Aggregations`; their buckets are also in `SubBuckets`, and a filter facet's are in its `NestedAggregation` too. Keys are text, a whole number in the invariant culture (`5`). Counts cover the main query's matches: a post filter narrows the hits but not the counts. Every provider returns a failed `Result`, before it asks the engine, for a `null` facet (`FacetQueries holds a null entry.`), a facet without an `AggregationName`, two facets of the same name at the same level, a term facet without a `TermFieldName`, a multi-term facet with fewer than two `Terms`, a `Size` below 0 or above 65,536 (Elasticsearch's default `search.max_buckets`), any other `IAggregationQuery` type, nested ones included, a facet nested inside itself, and nesting more than 16 levels deep; on Lifti every facet fails with its own message instead. The shared `FacetsTestBase` checks all of this on every provider.

`SortOrderField` is the `ISortOrderField` to put in `SortOrder`. Keys apply by `Order`, lowest first, and keys with the same `Order` keep their place in the list. Every provider, Lifti included, returns a failed `Result` for a `null` entry (`SortOrder holds a null entry.`) or an entry whose `FieldName` is `null`, empty or blank (`A SortOrder entry needs a FieldName.`), before it sends anything to the engine. The shared `SortingTestBase` checks both messages on every provider, and a two-key sort returning a fixed order on Elasticsearch, OpenSearch and Meilisearch; on Lifti it checks that the order is the one without `SortOrder`.

Setting `SearchDocument.Fields` to `null`, in code or by deserializing, gives an empty dictionary, so a document always has fields. `IIndexingServiceAsync.IndexDocumentAsync` returns a failed `Result` naming the fields whose value is `null` rather than a list, or naming the fields that hold a `null` value; use an empty list for a field with no values. `IndexMultipleDocumentsAsync` checks every document for `null` first, failing on a `null` entry too, and indexes none of them when one has a `null`. It then runs the validator on every document, and when it rejects one or fails, returns a failed `Result` with one error per such document, naming it and holding its id in the error's `id` metadata, and indexes none of them. Otherwise it passes the whole batch to the provider's `IndexMultipleDocumentsAsync` in one call, which writes each index's documents in one request on Lifti, and in requests of up to `BulkBatchSize` documents on Elasticsearch, OpenSearch and Meilisearch. What a document the engine rejects leaves stored differs per provider, as the table above says; the error names the ids that were not stored in its `ids` metadata, and says how many of that index's documents were indexed. Documents for several indexes are written index by index, so when one index fails the documents of another can already be stored. On success the indexing observers get one `OnNext` per document, and a failed `Result` sends nothing, even for documents already stored. A rejected `null` sends nothing to the indexing observers. `RemoveDocumentsAsync(index, ids)` returns how many documents it removed, counting a repeated id once and not counting an id that is not there; an empty list succeeds with 0 without calling the engine, and a `null` list or a `null` or empty id is a failed `Result` that removes nothing. A failure message names up to 20 ids, and the error's `ids` metadata holds all of them. On success the service sends one `DeleteDocumentRequest` per distinct id to its observers, and a failed `Result` sends nothing, even for documents already removed. The providers' own `IIndexingProviderAsync.IndexDocumentAsync` does not check this and stores the document. A document stored with `null` fields, a `null` field or a `null` value, through a provider or by another writer, is still searchable on every provider; Elasticsearch, OpenSearch and Meilisearch map hits through the same code, so they return `null` fields as no fields, a `null` field as an empty list, leave `null` values out of a list and return the same CLR types for the same stored value, and Lifti returns only ids.

`GetDocumentAsync(index, id)`, `CountAsync(query)` and `UpdateDocumentAsync(index, id, fields)` are default interface members of `ISearchProviderAsync`, `ISearchServiceAsync`, `IIndexingProviderAsync` and `IIndexingServiceAsync`, so a provider written before them still compiles and returns a failed `Result` naming itself. `GetDocumentAsync` returns `null` when the engine answers that the document or the whole index is not there, and a failed `Result` when it can't answer, such as on a 401 or 5xx; a `null` or empty id is a failed `Result`. `CountAsync` counts the documents `SearchAsync` would return for the same query, post filter included, and ignores `Page`, `PageSize`, `SortOrder`, `Properties`, `HighlightQueries` and `FacetQueries`. `UpdateDocumentAsync` replaces the values of each field it names and keeps the other fields, returning `true` when the document was updated and `false` when the document or index is missing; it creates neither, except that on Elasticsearch and OpenSearch an index deleted between the provider's index check and the update is created again by the engine, and on Meilisearch a document removed between the read and the write is stored again. An update with no fields, a `null` field or a `null` value is a failed `Result` on every provider, and `IIndexingServiceAsync.UpdateDocumentAsync` does not run the document validator, which checks whole documents. None of the three notifies observers. The shared `DocumentOperationsTestBase` runs these on every provider except Typesense, which does not implement them yet: a get of a stored document, of a missing document and in a missing index, an exact count with a page that holds one hit, a count in a missing index, an update that changes one field and keeps the others, a date included, searchable, and an update of a missing document and in a missing index, which creates nothing; a Meilisearch test counts past an index `maxTotalHits` lowered below the count.

On Elasticsearch and OpenSearch, `WriteVisibility` in `SharedIndexSettings` or an `Indexes` entry decides when a successful write returns. `Default` returns once the write is stored, and a search sees it after the next index refresh, about a second later; `WaitUntilSearchable` adds `refresh=wait_for` to index, delete and bulk requests and `refresh=true` to the delete by query of `RemoveAllDocumentsAsync`, so the write is searchable when the call returns. Whatever the setting, `RemoveAllDocumentsAsync` refreshes the index before its delete by query, which would otherwise skip writes not refreshed yet, and a failed refresh is a failed `Result` that removes nothing. An `Indexes` entry without it takes the shared value. Each call can then wait up to the refresh interval, and `IndexMultipleDocumentsAsync` waits once for each bulk request of `BulkBatchSize` documents. Meilisearch, Typesense and Lifti have no such setting, as their writes are already searchable on return.

Elasticsearch, OpenSearch, Meilisearch, Typesense and PostgreSQL validate their options at startup (`ValidateOnStart`) and whenever they are read: the connection string and authentication of the shared settings and of each `Indexes` entry after merging, `MaxResultWindow` (Elasticsearch, OpenSearch) or `MaxTotalHits` (Meilisearch) greater than 0, on Meilisearch `TaskTimeout` and `SettingsCheckInterval` not negative and `GeoField` and `PhraseFields` names it can filter on, on Typesense `SchemaCheckInterval` not negative, and on PostgreSQL that each connection string parses and names a host (a missing one is allowed when an `NpgsqlDataSource` is registered), that `Schema` fits in 63 bytes and that `TextSearchConfiguration` is a plain name; Typesense checks each of `AdditionalNodes` when it creates a client. The host fails to start with every failure listed, each naming its configuration path, and a missing section is one failure naming the section. After a reload to invalid settings, `SearchAsync` and the writes return a failed `Result` with the same messages. Lifti has no connection settings to check.

Meilisearch applies writes as tasks; the provider waits for each one, so a successful `Result` means the write was applied and a failed task returns Meilisearch's error with its code in the error's `code` metadata. If the wait times out (`MeilisearchOptions.TaskTimeout`, 30 seconds by default) the `Result` fails but the task is not cancelled, so the write may still be applied later; the error's `taskUid` metadata holds the task's uid. Writes also check the index's settings and, when something is missing, add the attributes the provider filters and sorts on and raise `pagination.maxTotalHits` to `MaxTotalHits`. Attributes added by others and a higher `maxTotalHits` are kept. A check is trusted for `MeilisearchOptions.SettingsCheckInterval` (5 seconds by default), so an index deleted elsewhere is fixed by the first write after that, and a higher `MaxTotalHits` by the next write.

## Test coverage

Provider-agnostic bases live in `BaseTests`. Lifti runs all three (`SubQueryTranslationTestBase`, `IndexingTestBase`, `QueryResultBaseTests`), plus its own search tests running every supported query type, boolean combinations, paging, sorting, result mapping and error paths; the unsupported query types are checked to fail, and the known defects (ignored `Field`, ignored paging and sorting, id-only hits, `CreateIndexAsync` replacing an index, a search creating a missing index) are pinned as they behave today. Its culture tests index and query a decimal, a `DateTime`, a `DateTimeOffset`, a date prefix and exponents end to end, and check that a decimal matches neither `35` through a Fuzzy query nor its words held in separate values. Its indexing provider tests cover bulk indexing across indexes, a repeated id in one batch, a rejected document leaving its own index unchanged but not another, remove-all, index deletion, every write that needs an index failing when none can be created, and removing one or many documents failing when the index lookup fails (removing never creates an index), throwing when cancelled, removing from the index the client factory returns, and not recreating an index deleted between the lookup and the remove; removing one document also keeps a thrown exception as the cause. The nested and top-level boolean semantics are shared tests there, so every provider must agree on them. Elasticsearch runs all three against a real server, plus its own search tests running every query type except `SpatialSearchQuery` against it, with boolean combinations, paging, sorting, result mapping and error paths. OpenSearch runs the same three bases and the same search tests against a real OpenSearch 3.3 server, plus provider tests for bulk indexing, remove-all and configuration. Both run the same mapping tests against their server: a `Keyword` field matched and sorted under its plain name, a `Text` field sorted on its `keyword` sub-field (case, multi-valued, `ignore_above` and a field named `fields`), a sort on `_score` kept on relevance when a `Text` field is named `_score`, an unmapped field kept dynamic, `SpatialSearchQuery` on a `GeoPoint` field, a `Date` field with the format `strict_date_optional_time||yyyy-MM-dd` accepting a `DateTime` and a `DateOnly` and finding each through `DateRangeQuery`, the mapping applied by `CreateIndexAsync` and added by `EnsureIndexExistsAsync`, a conflicting mapping and an unknown analyzer failing, and invalid options failing startup validation.
